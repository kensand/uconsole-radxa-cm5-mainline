# Session log: uConsole + Radxa CM5, RX image → mainline 7.2.9 on microSD

A record of what was actually done to get a **TXW500170B0-BL** uConsole with a
Radxa CM5 and the **AIO v2** booting the mainline kernel from this repo, starting
from a blank microSD. Dated 2026-10-10. This is the *real* sequence (with the
dead ends), distinct from [sd-boot-guide.md](sd-boot-guide.md), which assumes
Radxa's own Debian image as the base. Here the base was **AK-Rex's
ClockworkRadxa image** — that difference matters and is called out where it did.

> **TL;DR outcome:** the kernel in this repo (built against `linux-7.2.y`,
> v7.2.9) boots the TXW500170B0-BL panel, the OCP8178 backlight, the AIO v2's
> GPS/RTC, panthor GPU — all working from microSD. The RX BSP kernel is kept as
> the emergency entry. No fork of this repo was needed: it builds unchanged.

| Part | Detail |
|---|---|
| Chassis | ClockworkPi uConsole, 2026 revision |

| Module | Radxa CM5 (RK3588S), 8 GB |
| Adapter | HackerGadgets CM5 adapter |

## 1. Build (on the x86_64 host)

Cloned `linux-7.2.y` (v7.2.9) and applied this repo's additions exactly as the
README's step 2 describes — panel driver, OCP8178 backlight driver, the AXP
battery-status patch, and all five DTS/DTB sources. Then:

```bash
KDIR=$PWD ~/build-uconsole-kernel.sh        # KVER=7.2 default
```

**Result: clean build, zero errors, first try.** One harmless compiler warning
(unused variable `ctx` in `panel-cwu50.c:471`). Kernel release: `7.2.9-dirty`
(`-dirty` = the patched tree; expected, that's what `uname -r` prints).

Staged artifacts (`~/Work/uconsole-cm5-7.2.9/`):

```
Image-7.2                                      42 MB  kernel
rk3588s-radxa-cm5-uconsole.dtb                 87 KB  base DTB (serial console, on/off backlight)
rk3588s-radxa-cm5-uconsole-aio.dtb             88 KB  ← the one booted (AIO v2, OCP8178, no serial console)
rk3588s-radxa-cm5-uconsole-aio-lora.dtb        88 KB  (LoRa MISO-wire variant, not used)
modules-7.2.tar.gz                             92 MB  full module tree for 7.2.9-dirty
```

The config fragment is regenerated by the build script at
`~/Work/configs/uconsole-7.2.config` (source of truth, not `.config`).

**Why no fork:** every patch applied cleanly to v7.2.9 and the build succeeded
unchanged. The only upstream-worthy nit is that one warning.

## 2. The base image — RX ClockworkRadxa, *not* Radxa's

The guide assumes Radxa's `radxa-cm5-rpi-cm4-io_bookworm_cli_b3`. What was
actually flashed was **AK-Rex's** image from the
[ClockworkPi forum bring-up thread](https://forum.clockworkpi.com/t/bookworm-6-1-y-for-the-radxa-cm5-uconsole/16315):

```
ClockworkRadxa-Debian-12-Bookworm-lite-6.1.84.img.xz
```

Flashed with:

```bash
sudo xzcat ./ClockworkRadxa-Debian-12-Bookworm-lite-6.1.84.img.xz \
  | sudo dd of=/dev/sda oflag=direct conv=fsync bs=4M status=progress
sync
```

**Two things that were NOT true for this image** (the forum post's caveats, both
confirmed):

1. **Older panels only.** The RX image's panel support does not drive the
   TXW500170B0-BL. After flashing, the LCD was **completely dark** with a
   heartbeat status LED — the kernel booted but the panel wasn't driven. That is
   *expected* and is the reason this repo exists (its in-kernel `cwu50` driver
   handles both panel revisions at runtime).
2. **The "lite" variant has no GPU.** Fine as a bring-up/fallback base; it is
   not the daily driver. (The forum explicitly warns "do not get the lite for
   the Radxa, it has no GPU.")

**The RX image's real value here:** it gave a working U-Boot + a booted Debian
system + **HDMI out**, which became the diagnostic and deploy channel since the
panel was dark and there was no serial adapter handy. Login: `clockwork` /
`clockwork`.

Note: the RX image's `extlinux.conf` carried `fdtoverlays
/boot/dtbo/cwu50_panel.dtbo` — so it *does* ship a panel overlay, it just doesn't
init the -BL revision correctly. (Useful data point: the DSI path and panel power
were healthy; only the init sequence was wrong.)

## 3. Deploy the mainline kernel (over SSH to the RX system)

Device was on the LAN; it got a DHCP address (seen as `10.128.128.8x`). All
transfers were `scp` from the host.

```bash
# host → device
scp /home/kenny/Work/uconsole-cm5-7.2.9/* clockwork@<ip>:/tmp/
scp /home/kenny/git/uconsole-radxa-cm5-mainline/runtime/display-kick.service clockwork@<ip>:/tmp/
```

On the device:

```bash
sudo cp /tmp/Image-7.2 /boot/
sudo mkdir -p /boot/dtb-7.2
sudo cp /tmp/rk3588s-radxa-cm5-uconsole*.dtb /boot/dtb-7.2/

# modules: extract then rsync — NEVER `tar -C /` (replaces the /lib symlink on Debian)
mkdir /tmp/mods && tar xf /tmp/modules-7.2.tar.gz -C /tmp/mods
sudo rsync -a --no-o --no-g /tmp/mods/lib/modules/7.2.9-dirty /lib/modules/

# display kick: REQUIRED, or the first DSI enable wedges → grey screen
sudo cp /tmp/display-kick.service /etc/systemd/system/
sudo systemctl enable display-kick.service

# root PARTUUID (SD = mmcblk0; p3 is the ext4 root)
lsblk -o NAME,PARTUUID
#   mmcblk0p3  ef199cad-49f5-483e-85e5-4c5198f8abc5   ← used
```

## 4. Boot entries

The RX image's existing `extlinux.conf` had `l0` / `l0r` (the 6.1.84 BSP, with
`fdtdir /usr/lib/linux-image-6.1.84+/` and `root=UUID=...` + an initrd). Two
labels were appended. **Differences from the Radxa-style entries that matter:**

- `fdt /boot/dtb-7.2/...` — a standalone file, not `fdtdir /usr/lib/linux-image-...`
- `root=PARTUUID=...` — **not** `root=UUID=` (no initramfs in this kernel; a bare
  kernel can't resolve fs UUIDs)
- **no `earlycon=`** — the BSP entry has it and works; ours must not (UART4
  hard-hang before its clock is ungated)

```
label uconsole-72-mainline
	menu label uConsole mainline 7.2.9 (base DTB, serial console, amp hiss)
	linux /boot/Image-7.2
	fdt /boot/dtb-7.2/rk3588s-radxa-cm5-uconsole.dtb
	append root=PARTUUID=ef199cad-49f5-483e-85e5-4c5198f8abc5 rootfstype=ext4 rootwait rw console=ttyS4,1500000 console=tty1 consoleblank=0 loglevel=7 panic=10

label uconsole-72-aio
	menu label uConsole mainline 7.2.9 (AIO v2)
	linux /boot/Image-7.2
	fdt /boot/dtb-7.2/rk3588s-radxa-cm5-uconsole-aio.dtb
	append root=PARTUUID=ef199cad-49f5-483e-85e5-4c5198f8abc5 rootfstype=ext4 rootwait rw console=tty1 consoleblank=0 loglevel=7 panic=10
```

## 5. The U-Boot menu is not on HDMI — set `default` instead

**The one non-obvious thing this session cost time on.** The RX U-Boot prints
its menu to the **FIQ serial console, not HDMI**. On HDMI the boot is *straight
black → the `default` entry*; there is no menu to select from and mashing
Enter/Space does nothing. The first "boot attempt" therefore just ran `default
l0` (back to 6.1.84) — the build was fine, the entry simply was never selected.

**Fix that worked:** make the target entry the default, cold-start, and it boots:

```bash
sed -i 's/^default l0/default uconsole-72-aio/' /boot/extlinux/extlinux.conf
grep '^default' /boot/extlinux/extlinux.conf     # → default uconsole-72-aio
```

Then a cold start (poweroff → ~30 s → power on). **It booted, with the display
working.** This is the reliable way to switch kernels on this setup without a
serial adapter; the manual-menu path only exists on the FIQ/UART console.

## 7. The rotated-console gotcha (and its one-line fix)

**Symptom:** at the login prompt the text was rotated 90° — *while watching over
HDMI*. The DSI panel itself is correct.

**Cause:** `fb0` was bound to the **HDMI** connector (a 3840×2160 framebuffer —
not the 720p panel). With HDMI attached at power-on, rockchip-drm made HDMI
primary, so `console=tty1` rendered to the HDMI framebuffer, which has no panel
rotation applied. The DSI panel (with its DTB `rotation = <90>`) was fine.

**Fix that worked:** **unplug the HDMI and reboot.** With no HDMI sink, fb0
falls back to the DSI panel and the console is upright. No config change needed.

**Standing rule for this device:** don't leave HDMI plugged in at power-on if
you want the on-panel console upright. Under a Wayland compositor (sway/labwc)
this stops mattering entirely — it reads `rotation=90` from the DTB and applies
`output DSI-1 transform 90` by itself. The sideways console is only a
pre-desktop cosmetic. (If you do want the console on the panel while HDMI is
attached, the lever is making DSI primary — `video=DSI-1` on the kernel cmdline —
not tried in this session.)

## 8. needrestart nag

`needrestart` fires after every `apt` run claiming "newer kernel available:
6.1.84+" — a false positive: it only knows about `.deb`-installed kernels and
doesn't realise the running `7.2.9-dirty` is *newer*. **Do not reboot to "load
the new kernel"** (that drops you back to 6.1.84). Silence just the kernel hint:

```bash
echo '$nrconf{kernelhints} = 0;' | sudo tee /etc/needrestart/conf.d/no-kernel-hint.conf
```

## 8a. The Trixie upgrade — investigated, then deferred

We went to do the Debian 12 → 13 upgrade (guide step 6) and found the image is
**more Radxa-BSP-managed than the guide assumes**, which makes it the riskiest
step in the project. Findings, in case it's attempted later:

- **No `/etc/apt/sources.list`.** Sources are classic `.list` files in
  `/etc/apt/sources.list.d/`: `50-bookworm{,-backports,-security,-updates}.list`,
  `70-radxa.list`, `80-radxa-rk3588s2.list`, `90-vscodium.list`. (A sed over
  `*.sources` is a no-op here.)
- **The Radxa repo is bookworm-pinned** (`a=bookworm`, `n=bookworm`, no trixie
  component). A plain `full-upgrade` fights it; it must be disabled for the
  duration.
- **`u-boot-menu 4.2.2` + `rsetup 0.4.28` ARE installed** (plus the whole
  `radxa-*` BSP layer: `radxa-system-config-rockchip`, `radxa-desktop-branding`,
  `radxa-sddm-theme`, `radxa-overlays-dkms`, `task-radxa-cm5-rpi-cm4-io`, ...).
  This is exactly the layer that regenerates `extlinux.conf` and drops the
  mainline labels on an apt trigger — the guide's apt-hook + reference copy are
  *required* here, and the debian.md traps (GDM breakage, the `radxa-sddm-theme`
  postrm that bricks later `apt` runs, dpkg diversions) all apply.
- **Decision: defer Trixie.** The kernel (7.2.9) runs fine on bookworm; Trixie
  only adds Mesa 25 (sharper panfrost) and libgpiod v2 (needed solely by the
  `aio` tool / meshtasticd). Not worth the release-upgrade risk on a
  BSP-managed image. See §9 for where this left off.

## 8b. Rollback: how to get back to *this* Debian state

This section is the restore path if the later Arch install (or anything else)
goofs the SD. Two layers of insurance, in order of preference:

**1. The gold backup (made before the Arch install).** A tarball of everything
that is *not* a stock package — the running-kernel state, the boot config, the
tuned system files. Made with:

```bash
# on the Debian system, before any Arch work (confirmed paths, 2026-10-10):
sudo tar czf /tmp/uconsole-debian-7.2.9-backup.tar.gz \
  /boot /etc /root /usr/lib/modules/7.2.9-dirty
# then get it OFF the SD, to the host PC:
#   scp clockwork@<ip>:/tmp/uconsole-debian-7.2.9-backup.tar.gz \
#       /home/kenny/Work/uconsole-backups/
```

(`/usr/lib/modules/7.2.9-dirty` is the real path — `/lib` is a symlink to
`/usr/lib` on Debian. `/boot` carries the Image, both DTB dirs, and
`extlinux/extlinux.conf` with the four labels. `/etc` carries
`display-kick.service` and the needrestart config. Total ≈ 150 MB.)

**2. Rebuild from this log + the repo** (if the tarball is lost). The whole
state is reproducible:
- Base: `ClockworkRadxa-Debian-12-Bookworm-lite-6.1.84.img.xz` (re-flash, §2).
- Kernel: rebuild or re-copy the artifacts (§1, §3) — the build is unchanged.
- Boot entries: §4, verbatim, with `default uconsole-72-aio`.
- display-kick enabled (§3), needrestart silenced (§8).
- The only *non-reproducible* bit is any package installed by hand after bring-up;
  the tarball in (1) is what captures that.

**What is NOT in the backup and must be re-done after any restore:** nothing
critical — but re-verify `default uconsole-72-aio` in `extlinux.conf` and that
`display-kick.service` is enabled, since those are the two things that silently
change the boot experience.

## 10. Switching the base to Arch Linux ARM (2026-10-10, second half)

Chose Arch over the Trixie upgrade (§8a). Full write-up: [arch-install.md](arch-install.md).
The short version of what actually took, and what wasted time:

**What worked (the final method):**
1. Flash the **full RX image** to the SD (proven SPL+GPT+U-Boot+Debian rootfs).
2. **Offline** swap (uConsole off, SD in the host's reader): `find /mnt -mindepth 1
   -maxdepth 1 -exec rm -rf {} +` to wipe the ext4 root (`sda3`) contents, then
   `cp -a /tmp/archroot/. /mnt/`.
3. Drop the 7.2.9 `Image` + AIO DTB into the rootfs's `/boot`, modules into
   `/usr/lib/modules`.
4. `extlinux.conf` with **`root=PARTUUID=`** (not `root=UUID=`) + display-kick.
5. Boot → **Arch Linux ARM + 7.2.9-dirty**, panel up.

**What failed / cost time (so it isn't repeated):**
- **Hand-assembled boot layout** (blank card + `parted` GPT + `dd` first 16 MiB
  SPL): the RX image's GPT is not a standard GPT-at-0 (scrambled LBA fields);
  a naive `parted` table isn't found by U-Boot. Abandoned → flash the whole image.
- **Live `rsync --delete` swap** on the running Debian system: replaced `/usr`
  under a live system → most commands stopped working (`head`/`ls`/`cat`:
  "required file not found"). Re-flashed and did the swap **offline** instead.
- **`root=UUID=`** → "cannot open root device" at boot (UUID was correct per
  `blkid`). **`root=PARTUUID=`** fixed it — matches the original Debian 7.2.9 setup.
- **zsh gotchas:** `rm -rf /mnt/* /mnt/.*` aborts the whole line in zsh when a
  glob matches nothing (`no matches found`); use the `find -exec rm -rf` form.
- **Mount shadowing:** the empty FAT `sda2` mounted at `/mnt/boot` hid the ext4
  rootfs's real `/boot`; `umount /mnt/boot` to see it.
- **The RX image's real layout** (not the hand-rolled one): `sda1` 16M vfat
  "config", `sda2` 300M vfat "efi" (empty), `sda3` 476G ext4 "rootfs" (root +
  `/boot`). The kernel + `extlinux.conf` live on **`sda3`'s `/boot`**, not the FAT.

**NVMe observation:** on the 6.1.84 RX kernel the HackerGadgets NVMe board's
PCIe link failed (`rk-pcie ... PCIe Link Fail, LTSSM is 0x2` = no receiver), so
no `nvme0`. There is also a **116G eMMC** (`mmcblk1`) present. Re-check the NVMe
link under the 7.2.9 kernel (correct `pcie2x1l2`/PERST# in the DTB) — it may link
there. See Next steps §4.
